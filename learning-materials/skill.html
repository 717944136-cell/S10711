概念的个人解释

我的一句话理解：Skill = 给 Agent 的"岗位手册"——一个装着 SKILL.md（外加可选脚本和资料）的文件夹，平时只挂在墙上，Agent 发现当前任务对得上时才取下来照着做。

大模型本身是"什么都会一点、什么都不精"的通才。Skill 的思路不是去改造模型，而是把某类任务的程序性知识（怎么做、按什么流程、注意什么坑）写成文档打包，让模型在干活前先读手册。Anthropic 的类比很贴切：为 Agent 写一个 Skill，就像给新员工准备一份入职指南——指南本身不增加员工智商，但能让他把特定工作做得更专业、更稳定。

妙处在于它的格式简单得惊人：一个文件夹 + 一个带元数据的 Markdown 文件，就是全部。正因为简单，它后来被发布成了开放标准（agentskills.io），被几十个主流 Agent 产品采纳——写一次，到处能用。

🧭 类比：Skill 像图书馆里的操作手册卡片。图书管理员（Agent）脑子里记着每张卡片的索引卡（名称+一句话描述）；平时只看索引，等你说"帮我填个 PDF 表单"，他才抽出对应的手册完整读一遍，照着步骤干，需要时再翻手册附录里的表格和工具。手册管够、桌子不乱——这正好接上了上一个概念：Skill 是对抗上下文有限的手段。

核心机制或组成

① 结构：一个文件夹，一个入口

# Agent Skills 开放标准（agentskills.io）的目录结构 my-skill/ ├── SKILL.md # 必需：YAML 元数据 + 任务指令 ├── scripts/ # 可选：可执行脚本（确定性步骤交给代码） ├── references/ # 可选：参考文档（按需加载） └── assets/ # 可选：模板、资源文件

SKILL.md 的元数据最少只要两个字段：name（标识）和 description（说明这个 Skill 做什么、什么时候该用它）——后者尤其关键，Agent 全靠它判断何时触发这个 Skill。

② 渐进式披露（Progressive Disclosure）——设计的灵魂

层级加载什么何时加载
第一级name + description 元数据启动时全部预载进系统提示（很小的开销）
第二级SKILL.md 的完整正文Agent 判断与当前任务相关时才读
第三级捆绑的附加文件（references、脚本等）Agent 按需自主发现和加载

这直接回应了"上下文有限"的问题：Agent 用文件系统按需取用而不是全量读入，所以一个 Skill 能捆绑的资料量实际上没有上限。Anthropic 的 PDF Skill 就是范例——表单填写指令被分离到 forms.md，核心手册保持精简，只在填表时才读那个文件。

③ 代码与模型的分工

Skill 可以捆绑脚本。原则是：确定性的步骤交给代码（如提取 PDF 字段、排序、格式转换），模型负责判断和编排。代码执行不占上下文、结果可靠可重复——这是"token 生成"做不到的。

④ 生态：从厂商特性到开放标准

该格式由 Anthropic 发起、2025 年底作为开放标准发布；agentskills.io 列出的采纳方已包括 Claude Code、Codex、Gemini CLI、GitHub Copilot、Cursor 等数十个客户端。这意味着 Skill 成了一种可移植的程序性知识格式，类似"Agent 界的 Markdown"。

具体应用场景

场景：就发生在你这个仓库里——.workbuddy/skills/concept-learner/ 本身就是一个活例子。

你说"帮我学习『Skill』这个概念"，背后发生的事是：

  1. 发现（第一级）：Agent 启动时就已把 concept-learner 的 name 和 description 读进上下文——"输入概念名，生成结构化 HTML 学习资料"。此时手册正文还没读。
  2. 激活（第二级）：任务与描述匹配，Agent 完整读取 SKILL.md 正文，按其中写好的流程走：澄清定义 → 梳理机制 → 构思场景 → 识别易混点 → 检索可核查来源 → 按固定输出结构生成。
  3. 执行（第三级）：按"来源要求"逐条联网核实 URL，不编造链接；生成后按"自检要求"逐项检查 HTML 完整性。

对比一下没有 Skill 的情况：每次都要口头交代流程和格式要求，换个会话就忘、质量不稳定。Skill 把这套流程固化成了可重复、可版本控制、可分享的资产——这正是"手册"的价值。业界同类的真实例子还有 Anthropic 官方仓库里的 docx/pdf/pptx/xlsx 文档技能（驱动 Claude 的文档能力）等。

容易混淆的问题 / 使用边界

辨析关键区别（一句话）
① Skill vs MCP / 工具MCP 解决"连接什么"（把外部服务、数据接进来）；Skill 解决"怎么做"（把工作流程、领域知识写成手册）。Anthropic 明确将二者定位为互补：Skill 可以教会 Agent 编排 MCP 工具的复杂流程。
② Skill vs 系统提示 / 长提示词提示词常驻上下文、篇篇付费；Skill 平时只占一两行描述，正文按需加载——这正是渐进式披露的意义。把所有流程塞进系统提示，等于把整面墙的手册都摊在书桌上。
③ Skill vs 记忆记忆存"事实与偏好"（这个用户是谁、项目约定是什么）；Skill 存"程序性知识"（这类任务按什么步骤做）。一个回答"是什么"，一个回答"怎么办"。
④ Skill vs 插件 / 扩展传统插件是代码级扩展，需按宿主的接口开发；Skill 只是文档+可选脚本，写 Markdown 就能创建，且因开放标准可跨产品迁移。
⚠️ 边界与风险
  • 安全是第一边界：恶意 Skill 可以指示 Agent 窃取数据或执行非预期操作，捆绑的脚本和资源也可能藏东西。只从可信来源安装；不可信来源必须先审计（检查依赖、捆绑资源、要求联网的指令）。
  • description 决定生死：Agent 靠描述判断要不要用这个 Skill。描述含糊或过长（有 1024 字符上限），Skill 就可能永远不被触发，或在不该用时被触发。
  • Skill 不是免检代码：官方也强调示例仅供演示，用前要在自己的环境里充分测试——手册写得再好，也得验证它真的管用。

自测问题

Q1：一个 Skill 捆绑了 200 页参考文档，会不会把 Agent 的上下文撑爆？为什么？
不会。渐进式披露保证启动时只加载 name+description；200 页文档只有在任务真正需要时才被按需读取（第三级）。所以 Skill 可捆绑的信息量实际上没有上限。
Q2：写好一个 Skill 后发现 Agent 从不使用它，最可能的问题出在哪里？
最可能是 frontmatter 的 description 写得不好——它是 Agent 判断"何时触发"的唯一依据。描述要么没说清适用场景（该触发时不触发），要么太宽泛（不该触发时误触发）。按 Anthropic 的建议，应站在 Agent 的视角重写描述，并观察它实际如何使用。
Q3：公司要教 Agent 按自家品牌规范排版文档，并让 Agent 在任何支持 Skills 的产品里都能用。该用系统提示、MCP 还是 Skill？为什么？
用 Skill。理由：① 流程性知识适合写成手册（渐进披露、省上下文）；② Skill 是开放标准（agentskills.io），一次编写可跨 Claude Code、Codex、Copilot 等数十个客户端复用；③ 系统提示常驻耗 token 且绑定单一产品，MCP 只解决工具连接不承载工作流知识。
