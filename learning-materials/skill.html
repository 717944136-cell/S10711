学习目标

  • 能用一句话说清 Skill 是什么，并解释"为什么值得做成文件而不是每次口头交代"。
  • 能讲清"渐进式披露"三层机制，以及它如何与上下文窗口配合。
  • 能区分 Skill 与 Prompt / Tool / MCP，并照着写一个最简 SKILL.md。

核心问题

  • 既然可以直接在对话框里告诉 AI 怎么做，为什么还要专门做一个 Skill？
  • AI 怎么知道"什么时候该用哪个 Skill"？装很多 Skill 会不会把上下文撑爆？
  • Skill、Prompt、Tool、MCP 到底有什么不同？

个人解释（我的理解）

我的记忆锚点：Skill 是把"怎么做某类任务"的专家经验，打包成 AI 需要时能自己翻开看的工作手册。

一个 Skill 本质就是一个文件夹，里面至少有一个 SKILL.md 文件：文件顶部是 YAML 元数据（name＋description），告诉 AI"这个技能叫什么、什么时候该用我"；正文则写清具体怎么做。AI 平时只"扫一眼目录"，当任务匹配时，才把正文读进来照着执行——官方说法是"像给新员工准备 onboarding 材料一样，把专业知识打包给 AI"。

🧭 类比：Prompt 是"你顺口交代的一句话"；Skill 是"写好的岗位说明书/菜谱"。交代的话说完就忘，下次还得重讲；菜谱存在抽屉里（＝文件夹），每次要做这道菜（＝任务匹配）就拿出来照着做，还能不断改进、跟别人共享。
  • 对我最直观的例子：本仓库的 concept-explainer 就是一个 Skill——我把"学一个新概念"的完整方法写进 SKILL.md，于是同一套流程可以反复用于 Agent、上下文、Skill 以及以后任何新概念。
  • Anthropic 于 2025-10 正式发布 Agent Skills，2025-12 又将其发布为开放标准：同一格式可跨产品、跨平台复用。

核心机制 / 组成

Skill 高效的关键是渐进式披露（progressive disclosure）——信息分三层，用到哪层才加载哪层：

层级内容何时进入上下文
① 元数据YAML 头部的 name＋description（每个约百来个 token）启动时常驻（用于"该不该用我"的匹配）
② 正文指令SKILL.md 正文：工作流、最佳实践、注意事项任务命中 description 后读取
③ 附带资源脚本、模板、参考文档（可另放子文件）按需再读，用不到就不占窗口

一次触发流程示意：

# Skill 触发过程（以本仓库 concept-explainer 为例） 用户请求："用 concept-explainer 学习 MCP" │ ▼ AI 把请求与所有已装 Skill 的 description 比对（只花元数据的 token） │ 命中：concept-explainer —— "概念学习资料生成器…" ▼ AI 读取 .workbuddy/skills/concept-explainer/SKILL.md 正文 │ 获得七步生成流程、章节模板、资料来源与自检要求 ▼ 按流程执行 → 生成 learning-materials/mcp.html（必要时再读③子资源） 完成，并在 README / 关系说明中登记

一个最简 SKILL.md 长这样（YAML 必填 name 和 description）：

--- name: hello-demo description: 当用户说"你好/打招呼"时使用。教 AI 用固定的方式友好回应并自我介绍。 --- # 执行步骤 1. 用一句问候回应； 2. 简单介绍自己能做什么； 3. 询问用户今天想做什么。

为什么这与上下文强相关：因为只有元数据常驻，即使安装几十个 Skill，平时占用的窗口也很小；一旦触发才加载正文。这正是 Skill 能"装很多而不拖垮 AI"的原因，也呼应了 llm-context.html 里"上下文要精选、别塞满"的原则。

一个具体应用场景

场景：把"我的概念学习法"做成 Skill，反复使用（也就是本作业正在做的事）。

  1. 沉淀：我把学习一个概念的方法——先列学习目标与核心问题，再写个人解释、机制图解、应用场景、辨析、自测、真实来源——写成 .workbuddy/skills/concept-explainer/SKILL.md。
  2. 复用：在 WorkBuddy 中打开本仓库，对 AI 说"用 concept-explainer 学习 Agent"，AI 自动匹配并读取该 Skill，按里面的流程产出 agent.html；同样的请求再来两次，得到 llm-context.html 和 skill.html——同一套方法，零重复讲解。
  3. 迭代与共享：Skill 跟着仓库走（git 版本管理），以后觉得流程要改进，改一处 SKILL.md 即可；将来学 RAG、MCP 等新概念继续调用，甚至可以把仓库公开分享给同学。

其它真实例子：Anthropic 官方为 Claude 预置了处理 Excel / PPT / PDF 的 Skill；企业把"品牌规范""发布流程"做成 Skill，让 AI 干活时自动遵守。

容易混淆的问题 / 使用边界

容易混淆关键区别（一句话）
Skill vs 普通 PromptPrompt 是一次性、对话级的指令，每次重发；Skill 是文件化、跨会话、可版本管理、可带脚本资源的"可复用工作手册"，按需自动触发。
Skill vs Tool（工具）Tool 是 AI 能调用的确定性"手脚"（搜索、算数、调 API）；Skill 是教 AI"怎么把活干专业"的流程知识（工作手册）。Skill 常常指导 AI 何时、如何用 Tools。
Skill vs MCPMCP 是"把外部系统/工具接进来"的标准化协议；Skill 是"知识与流程"的打包格式。一个解决"怎么连"，一个解决"怎么干"，可互补使用。
Skill vs 记忆/数据库记忆存"事实"（记得什么）；Skill 存"程序性知识"（知道怎么做）。大量事实资料应放 Skill 的③级资源里按需读取，而不是塞进正文。
⚠️ 边界与注意事项：
  • description 写不好＝技能永远不被触发：它要同时说清"做什么"和"什么时候用"。
  • 触发后仍占上下文：正文要精简（官方建议正文控制在 5k token 内），复杂内容拆到③级资源。
  • 代码安全：Skill 可以带可执行脚本，能力越强风险越大——只安装/运行可信来源的 Skill。
  • Skill ≠ 万能：它只是"把已知做法固化"，解决不了模型本身能力不足或任务目标不清的问题。

自测问题

Q1：一个 Skill 的最简形态是什么？SKILL.md 顶部必须写哪两个字段？
一个目录＋一个 SKILL.md；顶部 YAML 必填 name 和 description（description 要说明做什么＋何时用）。
Q2：为什么安装很多 Skill 不会显著占用上下文窗口？
渐进式披露：平时只有元数据（name/description）常驻，约占百 token/个；正文和资源在任务命中后才加载。
Q3：用一句话区分 Skill 与 Tool。
Tool 是可执行的"手脚"（做什么），Skill 是指导性的"工作手册"（怎么做得专业），两者常配合使用。
Q4：如果某 Skill 的 description 写得含糊，会发生什么？
AI 无法在触发匹配时判断何时该用，Skill 形同虚设——description 直接决定技能是否会被发现。
Q5（开放）：Skill 里可以放可执行脚本吗？有什么风险？
可以，官方设计就支持用脚本做确定性操作（如排序、算表）。风险是执行了不可信代码可能危害系统，因此应只使用可信来源的 Skill。
