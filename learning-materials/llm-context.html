大模型的上下文（Context / 上下文窗口）

概念的个人解释

我的一句话理解：上下文 = 模型这一次推理时"看得见"的全部内容（以 token 计）——包括系统提示、对话历史、工具说明、检索来的资料和你的输入；上下文窗口就是这套"看得见"的容量上限。

大模型有一个反直觉的特点：它没有真正的记忆。每生成一个字，模型都是把"当前上下文"整个重读一遍再接着写——上一轮对话之所以"被记得"，只是因为程序把它塞回了这一轮的输入里。所以上下文更像是模型的工作台而不是仓库：桌面上摆着的它才看得见，桌面之外的一切等于不存在。

IBM 把上下文窗口直接类比为模型的"工作记忆"（working memory），并指出窗口里装的远不止用户输入：系统提示、RAG 检索的外部资料、格式符都在占位置。而 Anthropic 的工程博客则把"管理好这个工作台"上升为一门学问——上下文工程（context engineering）：在每一步筛选该放进窗口的 token，因为注意力是稀缺资源。

🧭 类比：上下文窗口像一张固定大小的书桌。训练知识是你"脑子里背过的东西"（随时可用但不可更新）；上下文是"此刻摊在桌上的文件"。桌子再大也有上限——塞太满会出现两个问题：放不下（超窗截断），以及桌子越乱越找不到关键纸条（注意力被稀释）。会干活的人不是把所有资料都堆上桌，而是按需取放。

核心机制或组成

① 计量单位是 token，不是字

模型不按"字"或"词"计量，而按 token（词元）——一个 token 可能是半个词、一个词或一个短语，中文通常比英文更"费 token"。粗略换算约 1 个英文单词 ≈ 1.5 token。所以"上下文长度 128K"指的是 token 数，不是能读 12.8 万个字。

② 窗口为什么有上限：注意力是 n² 的

Transformer 用自注意力（self-attention）计算每个 token 与其他所有 token 的关系，计算量随长度平方级增长——token 翻倍，算力需求变 4 倍。这就是为什么窗口不是无限大、长输入也更慢更贵。

③ 窗口里实际装了什么

# 一次请求的上下文构成（示意） 系统提示（角色、规则、行为约束） 工具定义（每个工具的名字+描述+参数说明，也占 token） 对话历史（多轮"你说/它答"的完整记录） 检索资料（RAG 注入的外部文档片段） 本轮输入（用户当前这条消息） ↓ 模型对以上全部内容做注意力计算 → 生成输出（输出也受单独的最大输出 token 限制）

④ 两个关键的"坑"

Context Rot（上下文腐烂）：Anthropic 指出，随窗口内 token 增多，模型准确回忆信息的能力会下降——注意力预算摊薄了。这与 2023 年的经典研究《Lost in the Middle》结论互相印证：关键信息放在开头或结尾效果最好，埋在长上下文中间时性能显著下降，即使号称支持长窗口的模型也不例外。

⑤ 长任务的上下文管理技术（Anthropic 三板斧）

技术做法适用
压缩 Compaction接近窗口上限时把对话总结成摘要，用摘要重新"开桌"。多轮来回的长交互
结构化笔记把关键结论持久化到窗口外的笔记/文件，需要时再取回。有里程碑的长任务
子智能体子 Agent 用干净窗口专注干一件事，只把精炼结果交回主 Agent。需要并行探索的复杂任务

Anthropic 的总原则：找到"最小且信息量最高"的 token 集合——上下文是边际收益递减的有限资源，不是塞得越多越好。

具体应用场景

场景：一个代码 Agent 帮我维护一个越来越大的项目。

项目有几十个文件，远超上下文窗口装不下，它这样应对"桌子有限"的问题：

  1. 不整仓上桌：启动时只加载一份精简的项目说明（类似 CLAUDE.md），记住"哪个目录大概放什么"，而不是把所有代码读进来——预加载最必要的信息。
  2. 按需取用：改 bug 时先用搜索工具定位到相关的两三个文件，只把这些读进上下文——这就是"即时检索"，类比人靠文件路径和书签找资料，而不是背下整个文件系统。
  3. 任务长了就压缩：连续修了十几个 bug 后对话历史逼近上限，它把此前的关键决定总结成摘要重开窗口，避免"桌子摆满后开始忘事"。
  4. 关键信息放对位置：给它的修改要求放在消息结尾而不是中间——因为研究显示首尾位置的召回效果最好。

这个场景解释了为什么"上下文窗口 200K"的模型仍需要 RAG、摘要和文件系统：窗口大小解决"放不放得下"，上下文工程解决"用得好不好"。

容易混淆的问题 / 使用边界

辨析关键区别（一句话）
① 上下文 vs 训练知识训练知识"长在参数里"（改不了、无需占窗口）；上下文是"本次推理临时给的资料"（随时可换，但占窗口、会话结束即失效）。让模型知道新信息只能靠上下文（或再训练）。
② 上下文窗口 vs 输出上限窗口决定"输入能看多少"，最大输出 token 是另一个独立限制——输入 200K 的模型可能一次只能输出 4K~16K。
③ 窗口大 ≠ 用得好能塞进去不代表能用好：Lost in the Middle 表明中间信息召回差、Anthropic 指出注意力预算会摊薄。判据是"有效上下文利用率"，不是窗口标称值。
④ 长上下文 vs RAG二者不是替代关系：长窗口让"整篇文档直接塞"成为可能，但成本高、易腐烂；RAG 只取相关片段，便宜精准。实践常混合：小规模直接上桌，大规模先检索再上桌。
⚠️ 边界与风险
  • 成本平方级：token 翻倍、算力约 4 倍，长上下文又慢又贵，不要无脑全量投喂。
  • 超窗即截断/失败：超过窗口的内容必须截断或摘要，模型不会"自动记住"被截掉的部分。
  • 窗口越长攻击面越大：更长上下文给注入、越狱类攻击留了更大空间，生产系统需配合护栏。

自测问题

Q1：昨天和模型聊过的内容，今天新开一个会话它为什么"忘了"？怎么让它"想起来"？
因为上下文不跨会话保存——记忆只是上轮对话被塞回了本轮输入。新会话的上下文是空的，所以"忘了"。要它"想起"就得把关键信息重新放进上下文：贴进来、放 RAG/笔记里按需检索，或用带持久记忆的系统。
Q2：一个 128K 窗口的模型，能否把一份 130K token 的文档完整处理？如果不能，有哪些办法？
不能完整放入，会截断或报错。办法：分段摘要后汇总；用 RAG 只检索相关片段；用"大海捞针"式的定位检索；或换更大窗口的模型——但注意即使放得下，中间位置的信息召回也未必好。
Q3：为什么"上下文窗口从 4K 涨到 200K"并没有让 RAG 过时？
因为窗口大小≠利用质量：注意力预算有限，塞满的长上下文存在 Context Rot 和中间信息召回差的问题，且成本平方级增长。RAG 用极小的相关片段命中同样的信息，更便宜、更准。二者是互补而非替代。
