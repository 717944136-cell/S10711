大模型的上下文（Context / 上下文窗口）

LLM Context · Context Window · 大模型课程概念学习资料 ②
🎯 入门→进阶👤 编程初学者📅 2026-09-07

学习目标

  • 能说清"上下文 / 上下文窗口"是什么，以及它和"训练数据"的本质区别。
  • 知道哪些内容会占用上下文、窗口满了会发生什么、有哪些管理手段。
  • 能解释"为什么理解上下文是理解 Agent 和 Skill 的关键一环"（三份资料之间的桥梁）。

核心问题

  • 模型在回答问题时，到底"看得到"什么、"看不到"什么？
  • 为什么聊了很久之后，AI 会"忘记"开头说过的话？
  • 上下文窗口越大，模型就越聪明吗？

个人解释（我的理解）

我的记忆锚点：上下文是模型"本次任务的工作台"，而不是它"毕业前读过的书"。

大模型生成每个回答时，只能参考"此刻被放进输入里的全部内容"——系统提示词、历史对话、你贴的文档、工具返回的结果、甚至它自己刚说过的话。这一整块"摊在桌面上能被看见的资料"，就叫上下文（context）；它的容量上限就是上下文窗口（context window），用 token 数量衡量。

🧭 类比：上下文窗口就像一张课桌，你一次只能在桌上摊开有限的书和笔记来写作业；放不下的只能收进书包（＝存档/长期记忆），或者干脆扔掉（＝被截断）。而训练数据相当于你从小到大读过的书，它们变成了你的知识，但写作业时你并不会把它们全摆在桌上——你能用的只是摆出来的那部分。
  • 模型"记得"很多知识，那是训练阶段沉淀在参数里的（长期）；模型"此刻能用"的，只有上下文里的（工作记忆）。
  • 自己输出的内容也会追加回上下文，成为下一轮的依据——所以多轮对话会越占越多。
  • Anthropic 官方把上下文称为模型的"working memory（工作记忆）"，这个词我记了很久。

核心机制 / 组成

一次请求中，上下文窗口里装的是这些（它们都计 token）：

# 上下文窗口 = 模型能看到的一切（示意） ┌─────────────────────────────────────────────┐ │ 系统提示词 System Prompt（角色/规则） │ │ 历史对话（用户消息 + 模型回答逐轮累积） │ │ 工具/函数定义（Agent 可用哪些工具） │ │ 工具返回结果（搜索结果、代码输出、报错…） │ │ 用户当前问题＋贴入的文档/图片 │ └─────────────────────────────────────────────┘ 每次输出也会追加进来 → 下一轮接着累积 ……直到接近窗口上限 N token（例如 200k / 1M）

窗口满了怎么办（上下文管理三板斧）

策略做法例子
截断 / 丢弃（FIFO）最早的内容先被挤掉，类似"先进先出"。聊天界面里最早的几句被系统悄悄遗忘
压缩 / 总结（compaction）把长历史浓缩成摘要，腾出空间（Anthropic 称为服务端压缩）。长会话自动生成"前面的结论摘要"再继续
精选 / 检索（只放相关的）不把整库塞进去，先检索出相关片段再放入上下文（RAG 思路）。Agent 只把命中问题的几页文档放进窗口

两个容易被忽略的真相：

  • 上下文腐化（context rot）：Anthropic 文档指出，token 越多，模型的精确度与信息召回反而下降——"塞得多"不等于"用得好"，精选内容和空间大小同样重要。
  • 长上下文的"中间遗忘"：研究（Lost in the Middle）发现模型对长文档中间部分的利用明显更差，重要信息尽量放开头/结尾，或拆成小段处理。

一个具体应用场景

场景：让 AI 把本仓库三份概念资料（Agent / 上下文 / Skill）对比总结成一张关系表。

  1. 直接全塞（反面示范）：把三份很长的 HTML 全文一次性贴进对话。若总长接近窗口上限，模型可能出现：开头要求"用表格输出"被遵守，但中间某份资料的核心观点被忽略，或总结出现"张冠李戴"——这正是 context rot / 中间遗忘的表现。
  2. 正确做法（上下文管理）：先告诉 AI 任务与输出格式（系统提示），再只粘贴每份资料的"个人解释"段落（精选），必要时分三次问再合并——每一步都让"工作台"保持干净、相关。
  3. Agent 视角的延伸：Agent 每调一次工具，返回结果都会进上下文；如果它把整个文件夹都读了，窗口很快被占满，就可能"忘"了最初的指令——所以 Agent 要会"挑着读、读完总结、再继续"。

这说明：会不会管理上下文，直接决定了大模型（以及基于它的 Agent）在真实任务里的表现。

容易混淆的问题 / 使用边界

容易混淆关键区别（一句话）
上下文 vs 训练数据训练数据＝模型参数里的长期知识（"读过书"）；上下文＝本次推理时可参考的输入（"桌上的资料"）。训练截止后的事模型并不知道，除非检索后放进上下文。
上下文窗口大小 vs 智能高低窗口大只代表"能放更多"，不代表更聪明；越长越可能 context rot，且成本越高。小窗口＋好检索往往更实用。
上下文 vs "聊天记录"聊天记录只是上下文的一部分；系统提示词、工具定义与返回、贴入文档都占上下文。
token 数 vs 字数容量与计费都以 token 计；中英文每 token 对应的字数因分词器而异（大致 1 个汉字≈1 token 上下），不能拿"字数"直接换算。
⚠️ 边界提醒：
  • 超窗的请求会报错或被截断，重要内容可能悄悄丢失——关键资料别放"窗口最中间"。
  • 放进上下文的内容会发送给 API 服务方：不要把密码、密钥、隐私直接贴进对话（这也是本仓库用 .gitignore 保护敏感文件的原因之一）。
  • 上下文管理是工程问题：优先用检索/摘要/缓存（如 prompt caching）控制成本与质量，而不是盲目加长。

自测问题

Q1：上下文窗口和训练数据是一回事吗？
不是。训练数据＝模型预训练时学进参数的长期知识；上下文窗口＝生成回答这一刻可参考的输入（工作记忆），用完即弃、每次重新组织。
Q2：为什么很长的对话里 AI 会"忘记"开头的内容？
对话内容累积超过窗口上限后，最早的内容会被截断（FIFO 丢弃）或先被压缩成摘要（compaction），细节自然丢失。
Q3：上下文越大越好吗？
不是。越长精确度与召回可能下降（context rot），成本也更高；关键是把"相关的、精选的"内容放进去并放在合适位置。
Q4：一个训练数据截止于去年的模型，"知道"今年发生的事吗？
不知道（除非模型具备联网检索能力并把结果放进上下文）。参数知识有截止时间，新信息必须通过工具检索进入上下文。
Q5：Agent 调用工具后，返回结果去了哪里？
作为"工具返回结果"写进上下文窗口，成为模型下一轮推理的依据——这正是"环境反馈"机制在上下文层面的体现。
